## Design — /owner "Pipeline" tab nesting (agreed)

- `OwnerPage` (`nextjs-shared/OwnerPage`) only supports a flat `{ label, content }[]` tab list —
  no built-in nested/sub-tab concept.
- Approach: nest a second `OwnerPage` instance as the content of the new top-level "Pipeline" tab,
  holding the four sub-tabs (Players, Masters, FIDE, Pipeline Log) — mirrors the existing pattern
  instead of building a new nested-tab mechanism.
- The nested `OwnerPage` gets its own `persistKey` (`'chess-owner-tab-pipeline'`) so its sub-tab
  selection persists independently of the top-level tab (`'chess-owner-tab'`).
- Resulting top-level tab order: Logging, Cache, **Pipeline** (→ Players, Masters, FIDE, Pipeline
  Log), Dataflow, Constants, Session Storage, Routing Maintenance.
- Scope: `src/app/owner/page.tsx` only — no `nextjs-shared` changes needed.

## Design (agreed)

- **Generic, all projects.** Lives in `~/.claude/skills/` (already global). The PLAN file each run creates goes in the current session's project `docs/plans/`, as `#plan` already does.
- **Name / trigger:** skill name `version-bump`; native slash form `/version-bump`; text alias `#bump`.
- **Bump source:** the user edits `package.json` (bumps the versions they want) *before* invoking. The skill never chooses, applies, or analyzes versions.
- **No test plan.** The skill does not write a `## Testing` section and does not run `#code`.
- **Flow:** the three skills in turn, straight through, no pause. If `#reinstall` fails (install / tsc / build), stop there — do not run `#commit`.
- **PLAN slug per run:** `dependency-version-bump-<YYYY-MM-DD>` — date-stamped so a repeat run never collides with an archived copy in `docs/archive/`.
- **`nextjs-shared` spec:** never edited (the Versions tab owns it). `#reinstall`'s existing git-ref re-resolution step is unchanged.

## SKILL.md contents to write

Frontmatter: `name: version-bump`, `version: 1.0.0`, `description` — "Use when the user sends `#bump` or `/version-bump`. Runs a dependency version bump end to end for the current project: `#plan` → `#reinstall` → `#commit`, in sequence, no pause. The user edits `package.json` before invoking; the skill does not choose versions, analyze packages, or write a test plan."

Body:

**Intro** — chains the three release skills for a dependency version bump; the user has already edited `package.json`; run the three steps in order, straight through, no confirmation between them; if `#reinstall` fails, stop and report, do not run `#commit`.

**Steps**
1. **#plan** — invoke the `plan` skill. Title `Dependency version bump`; slug `dependency-version-bump-<YYYY-MM-DD>`. `## Plan` steps:
   - [ ] Bump dependency versions in `package.json` (done by the user before this run)
   - [ ] Run #reinstall
   - [ ] Run #commit
   `## Changes` seeded with one fixed line: `- Dependency versions bumped in package.json; package-lock.json regenerated by #reinstall.` No `## Testing` section. Check off the first Plan step.
2. **#reinstall** — invoke the `reinstall` skill, run to completion. On any failure, stop and report; do not proceed. On success, check off the `Run #reinstall` step.
3. **#commit** — invoke the `commit` skill, run its full pipeline (tsc + build gate, patch version bump, `git add -A`, commit, push, archive the PLAN file). Check off the `Run #commit` step before it stages files.

**What NOT to do** — don't choose/apply version numbers; don't edit the `nextjs-shared` spec; don't write a `## Testing` checklist or analyze changed packages; don't pause for a `#code` trigger (the skill is the authorization); don't run `#commit` after a failed `#reinstall`; don't bump the app's minor/major version (`#commit` does the patch bump).
