## Redesign (superseding the original 2-step design above, per further discussion)

The plan above ("Build a FIDE ratings module" / the two "New pipeline step" items) has been
superseded by a genuinely separate, 5-stage, independently re-runnable pipeline, per explicit user
direction: "always have a multi step process even if less efficient... make every small step a
separate process which can be run independently" (saved as a general auto-memory note,
`feedback_debuggable_multistep_pipelines`). It also lives on its own dedicated page, not embedded
in the chess pipeline page, but still logs via the same `tpip_pipelinelog`/`logPipelineStep`
mechanism.

**Route rename** (user decision): the existing chess pipeline page moved from `/owner/pipeline` to
`/owner/pipelinegames`; the new FIDE pipeline lives at `/owner/pipelinemasters`. All references
updated (`owner/page.tsx` nav tiles, `owner/constants/page.tsx` consumer strings,
`ui/dataflow/sections.tsx`).

**New tables** (in addition to `tmst_master_players`'s `mst_first_name`/`mst_last_name`/`mst_fideid`
above, which stands as originally agreed):
- `tfzp_fide_zip` (`fzp_data text`) — raw downloaded zip, **base64-encoded** (not `bytea` — see gap
  note below), one row, truncate+refill each run
- `tfxm_fide_xml` (`fxm_seq integer`, `fxm_data text`) — decompressed XML in
  `FIDE_XML_CHUNK_SIZE`-character chunks (constant, agreed = 2,000,000), truncate+refill each run
- `tfpl_fide_players` (`fpl_fideid`, `fpl_first_name`, `fpl_last_name`, `fpl_rating`, `fpl_flag`) —
  full unfiltered FIDE snapshot (~562K rows), truncate+refill each run

**Gap found in `nextjs-shared`**: `table_write`/`table_query`'s typed `value`/`params` types don't
include `Buffer` at all (only string/number/boolean/null, or string[]/number[] for `table_write`) —
worth proposing as a `nextjs-shared` amendment in a session there, but not fixable from this
project. Worked around here by base64-encoding the zip into `text` instead of storing raw `bytea`.

**New constants**: `FIDE_XML_CHUNK_SIZE` = 2,000,000 (agreed value) and
`FIDE_XML_READ_BATCH_CHUNKS` = 5 (batch size for re-reading chunks during parse — user gave
latitude to pick a reasonable value here, just keep it an explicit named constant).

**Five independently-runnable stages** (steps 10-14, own Run button each, own page):

### Bug fix — Parse FIDE XML produced 0 rows
User ran the pipeline and step 12 (Parse) reported "0 parsed" despite reading all 80 chunks
(158,596,152 chars, the exact correct file size). Diagnosed via a read-only script against the
real staged `tfxm_fide_xml` data (no writes): this installed version of `sax` **uppercases** tag
names in non-strict mode (`"PLAYER"`, `"FIDEID"`, ...) rather than lowercasing them, so every
comparison against lowercase `'player'`/`'fideid'`/etc. in `fideStaging.ts` silently never matched
— zero rows were ever pushed. Fixed by calling `.toLowerCase()` on tag names before comparing
(`parseFideXml`'s `opentag`/`closetag` handlers), rather than depending on sax's exact casing
convention. Re-verified against the real staged data (read-only, no table writes): 562,890 players
parsed, Magnus Carlsen's row correct (2823, active), 156 active players rated ≥ 2600 — matching
every number confirmed earlier in this project's manual research. User needs to re-run step 12
(Parse), then 13 (Populate) and 14 (Refresh) on `/owner/pipelinemasters`.

## Next phase — replace the per-click "Search known masters" live loop

**Why**: `searchKnownMasters` (`ChessBoardView.tsx`) currently loops through every `mst_priority =
true` name and does one live chess.com search per name, per click. Flagging the top 156 as priority
(done above) made this impractical — 156 sequential requests, ~500ms apart minimum, "would take
hours."

**Direction agreed**: since the existing chess.com game-sync pipeline
(`sync.ts`/`runGameSync`, `api.chess.com/pub/player/{username}/games/{year}/{month}`) already works
for *any* chess.com username, sync a master's own real game history the same reliable way — no new
scraping — for whichever of the 156 also have a known chess.com handle. This is **not** the same DD
concept as `tpl_players.pl_player` (that means one of the small, curated set of players the whole
pipeline is personally built around) — a master's chess.com identity is a distinct, new DD item:
`mst_chesscom_handle`.

- [x] **Phase 1** — Added `mst_chesscom_handle` (text, nullable) to `tmst_master_players` +
      `scripts/schema.sql`. SQL given in chat, run manually.
- [x] **Phase 2** (revised twice during implementation) — extracts the handle from the element
      whose `data-presence-fide-id` attribute matches the row's own `mst_fideid` (chess.com embeds
      both attributes on the same element — more reliable than trusting the first username-looking
      string on a page, since a page can mention other players too). Verified against 3 real
      database rows first (Magnus Carlsen → `magnuscarlsen`, Hikaru Nakamura → `hikaru`, Javokhir
      Sindarov → `Javokhir_Sindarov05`), each confirmed via a raw `curl` fetch.
      **Bug found in real use**: the first version (`findMasterPlayerHandles`) looped all ~140
      eligible rows sequentially with a `MASTER_HARVEST_DELAY_MS` pause — only ~16/140 came back
      with a handle, scattered (not a clean cutoff), and specifically missed Carlsen/Hikaru/Caruana
      despite those exact names re-testing successfully in isolation moments later — pointing to
      chess.com's own anti-bot throttling triggering intermittently only at that sustained scale,
      not a logic bug. **User decision**: process one player per click instead of a big batch —
      `findNextMasterPlayerHandle()` picks the single highest-`mst_grade` row still missing a
      handle, processes just that one, and returns its result; the user re-clicks "Find Next
      Chess.com Handle" (renamed from "Find Chess.com Handles") on `/owner/masterplayers` as many
      times as needed, sidestepping the batch-scale throttling entirely. Also scoped to
      `mst_priority = true` (skips any FIDE-linked row not flagged priority — relevant once the
